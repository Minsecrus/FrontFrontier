# VI.7 区块链和 Web3 集成

Web3 前端主要服务于链上资产管理与去中心化应用（dApp）。与常规 Web 应用相比，它的身份认证建立在用户自持私钥的钱包之上，状态写入需支付 Gas 并等待区块确认，且链上交易不可逆。这使得 Web3 成为一个在工程约束、异步状态模型与安全边界上均明显区别于普通 Web 应用的专业领域专题。

## **VI.7.1 钱包连接**

- [**MetaMask**](https://metamask.io/)：主流的浏览器扩展与移动端自托管钱包，向页面注入标准的 EIP-1193 / EIP-6963 Provider。
- [**WalletConnect**](https://walletconnect.com/)：跨端开放通信协议，通过二维码或深度链接将移动端钱包与桌面或移动 Web 应用配对连接。
- [**Reown AppKit（原 Web3Modal）**](https://docs.reown.com/appkit/upgrade)：WalletConnect 生态当前的主力钱包接入组件库。查阅旧教程时需注意，许多资料仍沿用 **Web3Modal** 这一旧称。
- [**wagmi**](https://wagmi.sh/)：面向以太坊生态的 React Hooks 状态库，封装了钱包连接、合约读写、链切换与交易回执监听。
- [**RainbowKit**](https://www.rainbowkit.com/)：基于 wagmi 和 [viem](https://viem.sh/) 构建的 React 钱包连接弹窗与账户管理组件库。

## **VI.7.2 区块链交互库**

钱包连接、ABI 编解码、交易签名、Gas 估算与链上事件订阅都依赖专门的底层交互库：

- [**ethers.js**](https://ethers.io/)：成熟的以太坊及 EVM 兼容链交互库，采用模块化与面向对象设计，明确分离只读节点连接（Provider）与持有私钥的签名者（Signer）。
- [**web3.js**](https://web3js.org/)：早期的以太坊 JavaScript 库。ChainSafe 已于 2025 年 3 月 4 日[停止维护](https://blog.chainsafe.io/web3-js-sunset/)，GitHub 仓库已归档且不再发布更新。新项目不应再引入；存量项目应按官方迁移指南切换至 viem 或 ethers.js。
- [**viem**](https://viem.sh/)：以 TypeScript 编写的现代以太坊底层接口，提供无状态、可组合的函数式原语，支持按需 tree-shaking 与严格的 ABI 类型推导。

下表对比了三款 EVM 交互库的设计取向与维护现状：

| :---------------------------------- | :----------------- | :--------------- | :------------------------------------------------- | :----- | :----- | :-------------- | :---------------------------------- |

## **VI.7.3 Web2 与 Web3 前端范式对比**

Web3 强调链上资产、可验证状态与用户自持钱包，是一类特定的应用模型，而非所有 Web 产品的统一演进方向。它与传统 Web2 应用的核心差异体现在四个方面：

- **去中心化与用户所有权**：传统 Web2 服务的账号、数据与权限集中在平台数据库中；Web3 则将资产归属记录在由分布式节点维护的账本上，用户通过自己掌握私钥的钱包直接证明所有权并签署操作。
- **数据公开性与隐私边界**：公链上的交易历史与合约状态对所有人公开，钱包地址只是假名（Pseudonymous），一旦与现实身份产生交集即可被链上分析追踪；同时，私钥一旦泄露或遗失，资产无法通过传统“找回密码”流程恢复。
- **货币化与激励模型**：项目常引入代币、NFT、链上会员或治理投票等经济机制，这也带来了更高的合规审查、经济模型抗攻击与用户教育门槛。
- **跨应用互操作性**：遵循同一链上标准（如 ERC-20、ERC-721）的资产与合约接口天然开放，用户无需重新注册账号，即可用同一个钱包在多个 dApp 之间流转资产。

## **VI.7.4 dApp 开发中的前端挑战与解决方案**

直接将所有读写都放在主网合约上，会面临高昂的 Gas 成本、秒级至分钟级的区块确认延迟，以及无法直接执行复杂分页与全文检索的限制。因此，生产级 dApp 普遍采用**链上与链下协同的混合架构**：

- **链上确认资产，链下承载高频交互**：只将资产所有权变更、资金结算等核心状态提交到链上，而将非关键计算、缓存与高频状态同步留在传统 Web2 后端。例如，NFT 游戏只把道具归属记录在链上，匹配队列、排行榜、用户资料和消息通知均由链下服务处理。
- **引入 Layer 2 降低交易成本**：将高频合约交互部署在 [Optimism](https://www.optimism.io/)、[Arbitrum](https://arbitrum.io/)、[zkSync](https://zksync.io/) 等 Layer 2 扩容网络上，可显著降低单笔 Gas 费用并缩短确认时间。
- **事件驱动的链下索引与分层存储**：链上合约不适合存放大体积文件或支持复杂关系查询。常见做法是：将 NFT 图像与不可变元数据存入 [IPFS](https://ipfs.tech/)、[Arweave](https://www.arweave.org/) 或 [Filecoin](https://filecoin.io/) 等去中心化存储；后端监听链上事件日志（借助索引器、[Redis](https://redis.io/) 或 [Kafka](https://kafka.apache.org/) 异步消费），同步到结构化数据库中，向前端提供低延迟的查询 API。

## **VI.7.5 钱包集成与用户体验（UX）**

Web3 前端的体验瓶颈集中在钱包接入、密钥保管、异步交易反馈和防钓鱼安全四个环节：

- **多钱包连接与会话管理**：借助 Reown AppKit（原 Web3Modal）、RainbowKit 等组件库统一处理浏览器扩展、移动端扫码连接、链切换与断开重连，避免手写各家钱包的兼容逻辑。
- **私钥与助记词门槛**：要求新用户手动备份助记词极易造成流失。部分自托管方案采用**多方计算（MPC）**，将私钥拆分为多个分片分别保存在钱包服务商、用户设备与用户加密云备份中，签名时多方协同完成，免去手动抄写助记词的负担；但恢复流程依赖服务商的分片可用性，接入前需评估其恢复与跨平台导出机制。
- **网络检测与切换**：多链应用必须在发起交易前检查钱包当前连接的 `chainId`，网络不匹配时主动提示并引导用户一键切换目标链或添加自定义网络配置。
- **异步交易状态反馈**：链上交易从发起签名、广播进内存池到区块打包确认耗时不定，前端需提供明确的阶段反馈：
  - 对低风险的非资金操作可采用**乐观 UI 更新**（交易失败时回滚）；
  - 展示清晰的**待定状态提示**（如“交易已广播，预计需要 15–30 秒确认”），并在应用内直接呈现确认结果，同时附上区块链浏览器（如 [Etherscan](https://etherscan.io/)）链接供核验；
  - 对耗时较长的跨链或批处理操作，可通过 WebSocket 或通知机制在确认后提醒已切走页面的用户；
  - 交易报错时，将晦涩的底层 RPC/合约 Revert 错误转化为可操作的指引（如提示 Gas 过低、余额不足或授权额度不够）。
- **渐进式披露复杂概念**：对普通用户隐藏 Nonce、Hex 数据等底层术语，将代币授权（Approve）与兑换（Swap）、转账等高频路径做成意图清晰的步骤说明，仅在高级设置中暴露滑点与自定义 Gas 参数。
- **前端与 RPC 安全边界**：由于链上签名不可逆，前端安全防护直接关系用户资产安全：
  - **隔离私有 RPC 密钥**：带计费或高权限的 RPC 密钥只能存放在受控服务端（如不入库的 `.env`），由后端代理转发并做限流；若前端直连第三方 RPC，必须在服务商后台配置严格的来源域名（Origin/Referer）白名单、方法白名单与 JWT 鉴权。
  - **防范钓鱼与盲签**：严格校验合约地址与用户输入，发起签名或交易前在界面上用可读文本列明调用的合约、目标链、代币数量与授权范围，提醒用户核对域名与钱包弹窗内容。

## **VI.7.6 先从只读链上查询开始**

读取公开链上数据可以先建立稳定的网络、格式化和错误处理路径，再进入钱包连接与签名流程：

```ts
import { createPublicClient, formatEther, http } from "viem";
import { mainnet } from "viem/chains";

const client = createPublicClient({
  chain: mainnet,
  // VITE_ 变量会被打包进前端，这里只能放公开 RPC 或已限制来源域名的端点
  transport: http(import.meta.env.VITE_RPC_URL),
});

export async function loadBalance(address: `0x${string}`) {
  const balance = await client.getBalance({ address });
  return formatEther(balance);
}
```

Vite 会把所有 `VITE_` 前缀的变量原样写进构建产物，任何人都能在浏览器里看到。Infura、Alchemy 等服务的 RPC URL 通常内含 API Key，应让 `http()` 指向自己的后端代理地址，由服务端持有密钥并做限流；至少也要在服务商后台限制允许的来源域名和调用方法。

生产界面应显示当前网络、地址校验结果、RPC 错误和数据时间；涉及签名或交易时，先向用户说明合约、链、金额、手续费和不可逆影响，再进入钱包确认。
