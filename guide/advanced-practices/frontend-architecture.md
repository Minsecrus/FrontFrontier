# V.12 前端架构模式：扩展复杂应用程序

**目的**：为构建可扩展、可维护、高性能的 Web 应用提供结构化方法论，尤其适合项目复杂度持续增长的场景。

前端架构要解决的问题是：当页面、团队、业务规则和交付频率持续增长时，代码仍然能被理解、修改、测试和发布。

- **单体前端**：一个应用、一个构建入口、一个部署单元。  
  它适用于大多数中小型项目，开发体验直接，调试简单，部署链路短。只有当团队协作、发布节奏或技术边界已经成为真实瓶颈时，才需要考虑更复杂的拆分。
- **模块化单体**：仍然是一个应用和一个部署单元，但内部通过清晰的功能模块、依赖方向和公共层约束来管理复杂度。  
  对很多团队来说，这是比微前端更现实、更稳定的中间形态。
- **微前端**：将大型前端拆分为多个可独立演进的部分，重点在于组织协作、交付边界和团队自治。  
  实现方式包括 Module Federation、路由组合、iframe、Web Components，甚至只是仓库与发布流程层面的边界划分。
- **内容优先 / 预渲染架构**：通过 SSG、SSR、CDN、边缘缓存和 API 组合，为内容型和营销型站点提供更快的加载与更简单的交付。
- **全栈元框架架构**：通过 Next.js、Nuxt、SvelteKit、Astro 等框架，把路由、数据获取、渲染、缓存、部署和服务端能力整合在一起。  
  它能降低全栈交付成本，但也会让应用更依赖框架约定。

一个可扩展的前端架构通常需要关注以下边界：

- **功能边界**：按照业务能力组织代码，例如用户、订单、内容、设置，并在 components、utils、hooks 等横向目录之外保留业务聚合关系。
- **层次边界**：区分页面层、业务组件层、通用组件层、数据访问层、工具函数层，让依赖方向保持清晰。
- **状态边界**：明确本地 UI 状态、客户端共享状态、服务器状态、URL 状态和表单状态分别归属哪里。
- **数据边界**：把 API 调用、类型转换、错误标准化和缓存策略集中管理，让组件消费稳定的数据接口。
- **设计系统边界**：将基础组件、设计 token、交互规范和可访问性要求沉淀为共享能力，统一服务页面和业务模块。
- **运行时边界**：区分浏览器、服务器、边缘函数、构建期脚本和 Worker 环境，让代码运行在匹配的环境中。

在实践中，前端架构通常沿逐步收敛的路径演进：

1. 从能工作的页面开始，在重复和边界逐渐清晰后再抽象；
2. 当重复逻辑出现时，提取稳定的组件和工具；
3. 当业务模块变多时，按功能边界组织目录；
4. 当数据获取混乱时，建立统一的数据访问层；
5. 当 UI 不一致时，建设组件库和设计系统；
6. 当团队协作成为瓶颈时，再考虑 monorepo、包拆分或微前端。

## **表格：常见架构选择及适用场景**

| 架构方式 | 适合场景 | 主要收益 | 主要代价 |
| :--- | :--- | :--- | :--- |
| 单体前端 | 中小型应用、团队规模较小 | 简单直接、部署方便、调试成本低 | 规模变大后边界容易模糊 |
| 模块化单体 | 中大型业务应用 | 保持单体简单性，同时改善可维护性 | 需要团队遵守模块和依赖约束 |
| 微前端 | 多团队、多产品线、独立发布需求 | 团队自治、技术边界清晰 | 集成、性能、一致性和治理成本高 |
| 内容优先架构 | 文档、博客、营销页、内容站点 | 加载快、缓存友好、部署简单 | 高交互复杂应用需要额外设计 |
| 全栈元框架架构 | 需要 SSR、数据加载、服务端能力 | 端到端约定完整，交付效率高 | 框架绑定更强，迁移成本更高 |

架构设计最容易犯的错误，是把大型公司的解决方案提前套到小型项目上。  
好的前端架构，应该让团队更快、更稳地交付，并为未来增长保留清晰的演进空间。从单体到微前端的变化，通常来自组织和交付模型的变化。

## **V.12.1 用目录和依赖方向表达架构**

一个功能型前端可以先采用下面的目录边界：

```text
src/
├─ app/        # 路由、Provider、全局样式
├─ pages/      # 页面组合与路由入口
├─ features/   # 面向用户能力的业务模块
├─ entities/   # 领域对象与数据模型
├─ shared/     # 通用 UI、工具、类型和基础设施
└─ main.tsx
```

依赖方向可以写成一条可审查的规则：`pages -> features -> entities -> shared`。`shared` 不依赖业务层，`entities` 不读取页面路由，跨层调用通过公开 API 和类型契约完成。

```ts
// features/search/index.ts
export { SearchBox } from "./ui/SearchBox";
export { searchProducts } from "./model/searchProducts";

// pages/catalog/CatalogPage.tsx
import { SearchBox, searchProducts } from "@/features/search";
```

实践时可以把目录规则加入 ESLint import boundary、Code Owners 和 PR 检查。架构的有效性由依赖图、变更路径和新成员能否快速定位代码共同验证。

## **V.12.2 架构决策治理：RFC、ADR 与技术债务管理**

优秀的架构不仅是一张静态的系统设计图，更是一套持续治理的团队机制：

1. **RFC (Request for Comments) 提案流程**：
   - 任何涉及框架迁移、构建链重构、状态管理替换等重大架构变更，应在编码前发起结构化 RFC 征求团队评审：
     - **背景与痛点**：当前遇到了什么真实工程瓶颈？
     - **目标与非目标 (Goals & Non-Goals)**：本次变更要解决什么，明确不做什么以防范围蔓延。
     - **详细设计**：技术方案、依赖方向、对现有模块的侵入度。
     - **备选方案与权衡 (Trade-offs)**：为什么不选方案 B 或 C？
     - **迁移与回滚预案**：存量代码如何平滑灰度迁移，出现不可控故障时如何回滚。
2. **ADR (Architecture Decision Records 架构决策记录)**：
   - 在项目仓库根目录下的 `.adr/`（或 `docs/adr/`）维护轻量 Markdown 决策档案。
   - 记录每一次关键决策在“当时所知的信息、外部约束与最终权衡”，彻底杜绝“后人因不理解历史约束而盲目推倒重来、反复踩坑”的现象。
3. **技术债务（Tech Debt）量化与偿还预算**：
   - 将技术债务显式归入团队的 Tech Debt Backlog。
   - 团队应设立固定的工程重构预算（例如每个迭代固定保留 15%~20% 工程师时间），专项用于底层依赖升级、类型安全补齐与废弃代码剪枝。
