# V.11 UX 工程原则：增强用户体验

**目的**：专注于满足用户需求和期望，确保产品易于导航、响应迅速且高效。

前端开发者需要理解 UI/UX 的工程落点。一个组件是否好用，取决于样式还原、状态完整性、交互预期、错误恢复、键盘和屏幕阅读器支持，以及在真实数据和不同设备上的稳定性。

## **V.11.1 UX 工程的核心原则**

- **一致性**：相同含义的操作应使用相同的视觉样式、文案、位置和交互方式。熟悉的模式能减少理解成本，并建立用户信任。
- **可学习性**：界面应尽量让用户通过结构、文案和反馈自然理解，减少额外说明文字。
- **反馈循环**：用户的每个操作都应产生可见反馈，例如按钮按下、保存中、成功、失败、撤销入口或下一步提示。
- **视觉层次**：排版、颜色、间距、对齐和留白要帮助用户快速判断“哪里重要、现在能做什么、下一步是什么”。
- **错误可恢复**：错误提示需要说明原因、影响范围和可执行的修复路径。
- **响应式与多输入方式**：界面应适配窄屏、宽屏、触摸、鼠标、键盘和辅助技术，在真实设备约束下保持可用。
- **性能感知**：加载速度、响应性、骨架屏、乐观更新和过渡动画都会影响用户对“快不快”的判断。
- **可访问性**：包容性设计是组件质量的一部分。语义、焦点、对比度和键盘操作都应在设计和实现阶段被考虑。

UX 工程是一门综合性学科，它将技术实现、交互设计、认知心理学和产品目标连接起来。性能优化、可访问性、错误处理、国际化和组件设计最终都会汇聚到用户能否顺利完成任务。

## **V.11.2 组件级 UI 设计检查框架**

设计或实现一个组件时，需要同时关注视觉呈现和真实产品中的工作方式。可以从以下维度检查：

### **1. 用途与边界**

- 这个组件解决什么任务？
- 什么时候应该使用它，哪些场景更适合其他组件？
- 它是基础组件、业务组件，还是页面级模式？
- 它是否有更简单的替代方案？

例如，Modal 适合打断流程、处理必须立即确认的任务；补充信息展示更适合 Popover、Drawer 或页面内展开区域。

### **2. 信息结构**

组件内部的信息要有清晰优先级：

- 主标题：说明对象或任务。
- 辅助说明：解释限制、后果或下一步。
- 主操作：用户最可能或最应该执行的动作。
- 次操作：取消、返回、稍后处理、查看更多。
- 状态提示：加载、成功、失败、空数据、权限不足。

如果一个组件里所有文字、按钮和图标都在争夺注意力，用户就会失去判断方向。

### **3. 状态完整性**

一个可复用组件至少要考虑这些状态：

- 默认状态
- hover / active / focus
- disabled
- loading
- selected / checked / expanded
- success / warning / error
- empty / no result
- readonly
- skeleton 或 placeholder

很多 UI 问题出现在“提交中”“接口失败”“数据为空”“文字过长”“权限不可用”这些边界状态。组件文档和 Storybook stories 应优先覆盖这些状态。

### **4. 交互行为**

交互设计要明确以下问题：

- 用户点击后是否立即有反馈？
- 请求未完成时能否重复提交？
- 失败后能否重试？
- 危险操作是否需要确认或撤销？
- 组件能否用键盘完成同样操作？
- 移动端是否存在误触风险？
- 动画是否帮助理解状态变化？

对于高风险操作，撤销通常比二次确认更友好；但删除账号、付款、权限变更等不可逆操作，仍然需要更强的确认机制。

### **5. 视觉规范**

视觉设计要帮助用户扫描和判断：

- 文字层级是否清楚？
- 间距是否体现分组关系？
- 对齐是否稳定？
- 主按钮和次按钮是否容易区分？
- 色彩是否只用于装饰，还是承载了状态含义？
- 文字变长、多语言、数字变大时是否会溢出？
- 组件在深色模式和高对比环境下是否仍然可读？

视觉规范应尽量来自设计 token，例如颜色、字号、行高、圆角、阴影、间距、动效时长，并在组件之间保持一致。

### **6. 内容与文案**

组件文案直接影响用户是否敢操作：

- 按钮文案要描述具体动作。
- 错误提示要说明如何修复。
- 空状态要告诉用户下一步。
- label 应始终可见，占位符只作为示例或提示。
- 危险操作要明确后果。

例如，“保存失败，请稍后重试”比“错误”有用；“暂无成员，邀请同事加入”比“无数据”更能推动用户继续行动。

### **7. 可访问性**

组件级可访问性要落到具体实现：

- 使用正确的原生元素和语义。
- 所有可交互元素都有可见焦点。
- 键盘顺序符合视觉和任务顺序。
- 图标按钮有可访问名称。
- 错误提示与输入控件有关联。
- Dialog、Menu、Tooltip、Combobox 等复杂组件遵循对应 ARIA 模式。
- 状态信息应同时通过颜色、文字、图标或结构表达。

可访问性应该成为组件 API 和交互模型的一部分。

### **8. 工程实现**

一个组件是否可维护，也取决于 API 设计：

- props 是否表达语义？
- 是否支持受控和非受控用法？
- 是否支持组合式用法？
- 是否能接入主题和设计 token？
- 是否有稳定的测试选择器或语义查询方式？
- 是否覆盖关键状态的单元测试、交互测试和视觉回归测试？

组件 API 应把常见视觉变化收敛为稳定语义。比如 Button 可以有 `variant`、`size`、`loading`、`disabled`，并通过设计 token 和组合能力处理更细的样式变化。

## **V.11.3 高频组件示例**

### **Button**

Button 的核心是动作。设计时要明确主次层级、危险程度和反馈状态：

- 主按钮每个区域通常只保留一个，让视觉焦点集中在最重要的动作上。
- 加载中要锁定提交动作，并保留按钮宽度，保持布局稳定。
- 禁用状态要说明原因，尤其是在表单未满足条件时。
- 只有图标的按钮必须提供可访问名称。

### **Input**

Input 的核心是输入、校验和修正：

- label 应始终可见，占位符只作为示例或提示。
- 校验时机要克制：可以在用户离开字段、提交表单或输入稳定后再显示错误。
- 错误信息要靠近输入框，并说明修复方式。
- 对邮箱、手机号、金额、日期等格式化输入，要考虑复制粘贴和移动端键盘。

### **Modal / Dialog**

Modal 的核心是打断和决策：

- 标题要说明具体任务。
- 主操作和取消操作要清晰区分。
- 打开后焦点应进入 Dialog，关闭后焦点应回到触发元素。
- 复杂长流程更适合独立页面或 Drawer。

### **Table**

Table 的核心是扫描、比较和批量操作：

- 列名要稳定、简短、可理解。
- 数字、日期、状态等内容要有一致格式。
- 空状态、加载状态、错误状态要单独设计。
- 排序、筛选、分页、选择行和批量操作要有清晰反馈。
- 窄屏下要考虑列隐藏、横向滚动或转为卡片列表。

### **Toast / Notification**

Toast 的核心是轻量反馈：

- 适合提示“已保存”“复制成功”“同步失败”这类短反馈。
- 复杂解释或关键决策适合放在页面、Dialog 或详情区域中。
- 错误 Toast 应提供重试或查看详情入口。
- Toast 数量应有上限，并为主要操作区域留出空间。

## **V.11.4 如何验证 UX 是否有效**

组件设计完成后，需要用真实场景验证：

- 用真实或接近真实的数据测试长文本、空数据、大数字、多语言和异常状态。
- 用键盘完整走一遍主要流程。
- 用移动端尺寸检查触摸目标、遮挡和滚动。
- 用慢网速或接口延迟检查 loading、skeleton 和重试。
- 用 Storybook 或组件文档展示所有关键状态。
- 通过埋点、漏斗、RUM、用户反馈和可用性测试验证用户是否真的能完成任务。

好的 UI/UX 需要让用户在真实限制下仍然能理解、操作、恢复并完成目标。前端工程师的价值，正在于把这种体验落实到组件、状态、性能和可访问性这些可执行的工程细节中。
