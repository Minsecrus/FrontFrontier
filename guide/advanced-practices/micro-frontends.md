# V.14 微前端架构

微前端架构是大型组织应对复杂前端系统的一种手段：它把一个庞大的前端系统拆分为多个可独立演进的部分，以支持团队自治、分阶段迁移和独立发布。**微前端是一种高成本、高治理要求的组织级方案，适合多团队、多产品线、独立发布诉求明显的场景。**

## **V.14.1 实现方案对比**

**[Module Federation](https://module-federation.io/)** 是当前最常见的微前端技术路线之一，它的核心价值是**运行时共享模块**。其生态已经延展到 **Webpack + Rspack**，并出现了 **Native Federation** 等更贴近浏览器标准的探索。它的优势是细粒度共享组件和依赖、支持渐进接入；难点则在于协调依赖版本、隔离运行时故障、管理样式和路由边界。

[**Single-SPA**](https://single-spa.js.org/) 是更偏“编排层”的微前端方案。它擅长把不同技术栈的应用通过统一入口和生命周期组织起来，适合多框架并存、需要逐步拆单体的场景。代价在于样板代码更多、生命周期管理与跨应用通信的治理负担更重。

[**Qiankun（乾坤）**](https://qiankun.umijs.org/zh) 是基于 Single-SPA 的增强方案，提供了更完整的沙箱、资源加载和通信能力。它在国内企业项目里仍然很常见，尤其适合需要较强隔离和较低接入门槛的团队。

## **V.14.2 核心挑战与解决方案**

**路由管理**的挑战在于主应用和子应用都有自己的路由系统，需要协调 URL 与激活状态。常见方案是主应用统一路由前缀、子应用管理内部路由，或使用统一编排层控制激活规则。最重要的原则是：**边界稳定、回退容易、URL 仍然可理解**。

**状态共享**的挑战在于共享必要信息、同时保持微应用的独立边界。实践上更推荐共享少量稳定契约，例如认证态、主题、租户信息、埋点接口；大块可变业务状态应留在各自微应用内部管理。

**样式隔离**的挑战在于不同微应用可能使用不同 CSS 框架或命名约定，导致全局样式互相污染。常见隔离手段包括：

- **CSS Modules**：在构建期对类名进行哈希化，确保样式仅在局部组件作用域生效。
- **CSS-in-JS**：在构建期或运行时自动生成唯一类名，将样式限定在组件边界内。
- **Shadow DOM**：利用 Web Components 的原生 Shadow DOM 隔离样式，但会引入主题穿透、全局弹层挂载和样式覆盖等额外复杂度。
- **BEM / 命名约定**：通过严格的微应用前缀与层级命名规范降低类名冲突风险。
- **Qiankun 样式沙箱**：在子应用挂载与卸载时动态增删样式表，或通过改写 CSS 选择器添加作用域前缀来减少样式污染。

**JS 隔离**的挑战在于不同微应用可能读写同名全局变量、修改内置对象原型或加载冲突版本的依赖。常见隔离手段包括：

- **Qiankun JS 沙箱**：基于 `Proxy` 代理 `window` 等全局对象，隔离各微应用的全局属性读写与副作用。
- **Webpack Module Federation 共享依赖**：通过 `shared` 配置协调公共依赖版本，必要时开启 `singleton` 确保运行时只加载单个实例。
- **严格的 ES Modules 模块化**：将状态与副作用收敛在模块作用域内，禁止向 `window` 挂载业务变量。
- **iframe**：拥有浏览器原生的独立 JS 执行环境与文档上下文，隔离最彻底，但代价是跨窗口通信、路由同步、全局弹层和加载性能更难处理。注意 Web Components / Shadow DOM 仅隔离 DOM 与 CSS，不隔离 JS 全局作用域，不能充当 JS 沙箱。

下表对比了三种主流微前端方案的核心定位、工程收益与治理代价：

| 特性/方案        | [Module Federation](https://module-federation.io/)                          | [Single-SPA](https://single-spa.js.org/)             | Qiankun（基于 [Single-SPA](https://single-spa.js.org/)） |
| :--------------- | :-------------------------------------------------------------------------- | :--------------------------------------------------- | :------------------------------------------------------ |
| **核心定位**     | 运行时共享模块                                                               | 应用编排与生命周期管理                               | 企业级增强编排层                                        |
| **典型优势**     | 细粒度共享依赖、渐进迁移、Host/Remote 模式灵活                               | 多框架混合、路由驱动、拆单体友好                     | 沙箱、资源加载、隔离能力更开箱即用                      |
| **主要代价**     | 版本协调复杂、运行时耦合风险、调试成本高                                     | 生命周期样板多、治理成本高                           | 对底层机制理解仍然必要，且复杂度不会真正消失            |
| **打包/运行要求** | 常见于 Webpack / Rspack 生态                                                 | 更偏框架无关                                         | 更偏框架无关                                            |
| **理想场景**     | 需要共享组件/依赖的大型前端平台                                               | 多框架并存、逐步拆单体                               | 国内企业项目、需要更强隔离和治理能力                    |

微前端真正要解决的是**组织扩张导致的协作与交付瓶颈**。当团队规模、发布节奏、历史包袱和技术异构程度仍处于可控范围内时，模块化单体、Monorepo、设计系统和更清晰的目录依赖边界，通常能以更低成本解决问题。

## **V.14.3 用事件契约连接微应用**

微应用之间应通过版本化、可序列化的事件传递业务意图，并为监听器提供清理路径：

```ts
type CartUpdatedDetail = {
  version: 1;
  itemCount: number;
  source: "catalog" | "cart";
};

export function publishCartUpdated(detail: CartUpdatedDetail) {
  window.dispatchEvent(new CustomEvent<CartUpdatedDetail>("cart:updated", { detail }));
}

export function subscribeCartUpdated(handler: (detail: CartUpdatedDetail) => void) {
  const listener = (event: Event) => {
    handler((event as CustomEvent<CartUpdatedDetail>).detail);
  };

  window.addEventListener("cart:updated", listener);
  return () => window.removeEventListener("cart:updated", listener);
}
```

契约应定义事件名称、版本、字段、来源、错误处理和兼容周期。共享状态、依赖版本和跨应用导航也应记录在同一份平台文档中。
