# III.10 设计协作能力：从设计意图到可维护界面

设计文件承载着内容、布局、组件和交互约束。前端开发者需要把这些约束翻译成可维护的代码。

[Figma](https://www.figma.com/)、[Sketch](https://www.sketch.com/) 和 [Zeplin](https://zeplin.io/) 是协作过程中的代表性工具；它们帮你读取和传递信息，组件设计、状态建模和工程判断则由团队负责。

## **III.10.1 先读懂四类信息**

拿到设计稿时，先回答四组问题：

1. **内容层级是什么？** 哪些是页面标题、主要操作、辅助信息和重复列表？这决定 HTML 语义和组件边界。
2. **布局约束是什么？** 元素是固定宽度、随容器伸缩，还是在断点处换行？这决定 Flexbox、Grid、流式布局和容器查询的选择。
3. **哪些规则可以复用？** 颜色、字号、间距、圆角、组件和图标是否来自已有系统？这决定 token 与组件的复用方式，并减少页面内的重复定义。
4. **界面会怎样变化？** 输入、等待、失败、空数据、权限不足、移动端和键盘操作时会发生什么？这决定状态、路由、动画和无障碍实现。

[Figma Dev Mode](https://help.figma.com/hc/en-us/articles/15023124644247-Guide-to-Dev-Mode) 可以查看尺寸、间距、变量、组件属性、版本差异和交付状态；Sketch 的 Inspect 能提供类似的检查入口。开发者以这些约束为依据，把自动生成的 CSS 当作参考。

例如，设计稿中一张宽 320px 的卡片，可能表示“桌面稿里的当前结果”，也可能表示“组件最大宽度为 320px”。不先确认约束就照抄像素，到另一种屏幕上就会失效。

## **III.10.2 把设计语言映射成代码语言**

设计工具和前端代码表达方式不同，描述的却是同一套产品规则。下表中的工具能力就是这种映射的例子：

| 设计中的信息 | 代码中的表达 | 工具示例说明 | 实现时要确认 |
| :--- | :--- | :--- | :--- |
| **Auto Layout、对齐与间距** | Flexbox、Grid、gap、padding、换行和尺寸约束 | Figma Auto Layout 或 Sketch Smart Layout 显示元素之间的关系 | 是固定结果还是响应式规则；内容变长后是否仍成立 |
| **Variables、Styles 与 Modes** | CSS 自定义属性、主题对象、Tailwind theme、Style Dictionary token | [Figma Variables](https://help.figma.com/hc/en-us/articles/15339657135383-Guide-to-variables-in-Figma) 可复用颜色、尺寸等值，并用 mode 表达主题或环境差异 | token 的语义名称、作用域、别名和默认模式 |
| **Components 与 Variants** | 组件、props、slots 和组合关系 | Button 的 size、tone、disabled、loading 等设计变体可以映射为组件 API | 哪些组合有效，哪些状态互斥，是否已有代码组件 |
| **Prototype 与交互连线** | 路由、事件、状态机、焦点管理和动画 | Figma Present 或 Sketch Prototype 用来说明流程和状态转换 | 失败、返回、重复操作、减少动态效果等边界是否定义 |
| **设计组件与真实实现的关联** | Story、文档、源码路径和版本 | [Figma Code Connect](https://developers.figma.com/docs/code-connect/) 可以把设计组件映射到代码库中的真实组件，并在 Dev Mode 展示更贴近项目的用法 | 映射是否指向当前版本，示例是否符合团队约定 |

这张表提醒开发者：每读到一个视觉值，都要判断它属于哪一层；团队可按自身流程选用工具。

- 只在当前页面出现的一次性偏移，可以是局部样式。
- 多处重复的品牌色和间距，应优先成为 token。
- 反复出现且有状态变化的结构，应优先成为组件。
- 完整组件规格同时包含视觉效果和交互边界。

设计稿中的 Variables 和组件变体有助于发现规律，但 token 命名、组件 API 和兼容策略最终仍要在代码侧确定。

## **III.10.3 用一个表单检查完整状态**

假设要实现“修改账户资料”表单。默认设计稿可能只有头像、姓名输入框和保存按钮，但真实产品至少还需确认：

1. **初始状态**：已有资料从哪里加载？字段为空时显示占位符还是空值？
2. **输入状态**：遇到长姓名、不同语言、粘贴内容和自动填充时，布局是否保持完整？
3. **校验状态**：错误在失焦、提交还是输入时出现？错误文案怎样与输入框关联？
4. **提交状态**：保存中是否禁止重复提交？切换文案时按钮宽度是否保持稳定？
5. **失败状态**：网络失败、权限失效和服务端字段错误分别怎样提示？用户输入是否保留？
6. **成功状态**：显示 toast、页面内提示还是跳转？屏幕阅读器能否感知结果？
7. **环境变化**：窄屏、键盘导航、高缩放比例和减少动态效果偏好下是否仍可用？

这个例子揭示了设计协作的关键：设计原型负责表达主要意图，开发实现负责把意图补成可运行的状态系统。发现缺失状态时，应把问题评论到对应节点或任务上，由团队共同确认答案。

完成实现后，可以在 [Storybook](https://storybook.js.org/) 中展示默认、错误、加载、禁用和成功等状态，再通过交互测试或视觉回归，确认这些状态没有随代码变更而丢失。

## **III.10.4 按责任建立单一事实来源**

实际协作中，常见设计稿与开发版本错位、代码组件与设计属性不同步的问题。单一事实来源要求明确每类信息的负责人、有效版本和同步方式。

可以建立这样的责任链：

- **设计意图与交付范围**：在 Figma 中标记已准备好开发的页面、组件和版本，并把讨论绑定到具体节点。
- **稳定交付快照**：需要严格发布与归档的团队，可以用 Zeplin 等平台保存已确认的画板、注释和版本。
- **真实组件行为**：以代码和 Storybook 为准，因为只有它们能展示浏览器中真正运行的 props、状态和无障碍行为。
- **变更原因与验收结果**：放在 issue、PR 和测试记录中，留下可追踪的决策。
- **设计与代码互链**：用 Code Connect、组件链接或明确命名，把设计组件指向对应实现。

小团队通常用 Figma + Storybook + PR 就能形成闭环；设计系统较大、发布批次较多的团队，可以引入专门的交付与版本治理工具。流程是否成熟，体现在每类信息是否有明确负责人和有效版本。

## **III.10.5 前端开发者的设计协作清单**

拿到设计稿后，可以按以下顺序检查：

1. **确认范围**：哪些页面、组件和状态属于本次开发。
2. **读取结构**：识别布局、层级、组件边界和响应式约束。
3. **提取规范**：确认颜色、字体、间距、圆角、阴影是否来自设计 token。
4. **映射组件**：优先复用现有组件库，再决定是否新增组件或扩展 props。
5. **验证交互**：确认流程、动画、错误状态、空状态、移动端和无障碍细节。
6. **管理资源**：图标优先 SVG，照片按清晰度与体积选择格式，能用 CSS 或组件实现的装饰元素不必导出。
7. **留痕沟通**：把问题评论到具体节点，必要时链接到 issue、PR 或 Storybook story。

设计协作依靠一条稳定的翻译链：**设计说明意图与约束，工具帮助读取和传递，代码再将其落实为可维护、可测试的产品行为。**
