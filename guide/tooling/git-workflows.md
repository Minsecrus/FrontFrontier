# III.7 Git 工作流与团队协作

Git 作为分布式版本控制系统，是现代软件开发不可或缺的工具。然而，仅仅掌握 [Git](https://git-scm.com/) 命令远远不够，团队需要一套行之有效的工作流来规范代码提交、分支管理和协作流程，确保代码质量、提高开发效率、降低集成风险。

## **III.7.1 主流 Git 工作流模式**

[**GitFlow**](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow) 是高度结构化的分支模型，定义了长期存在的主分支（master 和 develop）以及短期存在的支持性分支（feature、release、hotfix）：

- **master**：存放随时可部署的生产代码。
- **develop**：集成所有新功能的开发成果。
- **feature**：从 develop 创建，用于开发新功能，完成后合并回 develop。
- **release**：从 develop 创建，用于准备新版本发布，在此测试、修复 bug，完成后合并到 master 和 develop。
- **hotfix**：从 master 创建，用于紧急修复生产 bug，完成后合并到 master 和 develop。

GitFlow 的优势：

- 不同类型的分支用途明确，职责清晰。
- 适合有固定发布周期的项目（如企业软件、受监管行业），release 分支为测试和 QA 留出了独立阶段。
- master 分支始终保持生产就绪状态，多个功能可以并行开发而互不干扰。
- 紧急 bug 可以通过 hotfix 快速修复并部署，不影响主开发流程。

GitFlow 的劣势：

- 分支数量多，管理和合并操作复杂，需要严格的分支规范和团队纪律。
- 多步骤发布流程对持续集成/持续部署（CI/CD）而言过于僵化，可能拉长发布周期。
- 长期存在的分支（develop、release）容易与主线分歧，增加合并冲突的风险。
- 规则和策略较多，新成员的学习成本较高。

[**GitHub Flow**](https://docs.github.com/en/get-started/quickstart/github-flow) 是轻量级、基于分支的工作流，围绕 main（或 master）分支和短期特性分支展开：

1. 从 main 分支创建新的特性分支。
2. 在特性分支上修改并频繁提交，每次提交都应包含一个独立、完整的变更。
3. 通过 Pull Request（PR）审查和讨论代码。
4. PR 通过审查后合并到 main 分支，并立即部署或准备部署。

GitHub Flow 的优势：

- 分支模型极简，易于理解和实施。
- 鼓励频繁集成和部署，适合持续交付/部署。
- PR 可以触发 CI/CD 流水线，便于接入自动化测试和部署。
- PR 集中了代码审查和反馈，促进团队协作。
- 每个变更都在独立分支上完成，历史清晰，易于追踪和回滚。

GitHub Flow 的劣势：

- 缺乏正式的发布结构，不直接支持版本管理、热修复分支或维护分支。
- 所有变更都直接合并到 main，如果代码审查和测试不严格，引入破坏性变更的风险较高。
- 特性分支生命周期短，单次合并的冲突范围较小；但在活跃项目中，多个分支同时修改相近代码时仍会冲突，需要经常同步 main。
- 不适合需要长期发布规划或严格 QA 阶段的项目。

[**Trunk-Based Development (TBD)**](https://trunkbaseddevelopment.com/)（主干开发）的理念是所有开发者都直接或通过短生命周期分支向主干分支（通常是 main）提交代码，并用功能开关（Feature Flags）控制新功能何时对用户可见。其优势是分支开销和合并复杂度都很低，适合高频 CI/CD 和持续部署；代价是对自动化测试、代码质量和团队纪律要求很高，需要成熟的测试流水线。

## **III.7.2 代码审查（Code Review）的重要性和流程**

代码审查是提高代码质量、发现缺陷、促进知识共享和确保团队规范的重要实践。其作用体现在：

- **提高代码质量**：通过同行评审发现潜在 bug、逻辑错误、性能瓶颈和安全漏洞。
- **知识共享**：团队成员通过审查了解彼此的代码，学习最佳实践，提升整体技术水平。
- **保持一致性**：落实编码规范、设计模式和架构原则。
- **降低维护成本**：更清晰、更健壮的代码减轻未来的维护负担。
- **增强团队协作**：形成积极的反馈文化，提升团队凝聚力。

代码审查的流程与最佳实践：

- **明确流程**：约定 PR 的生命周期（草稿、待审查、请求修改、批准、合并）和各阶段的责任人。
- **控制规模**：每次审查的代码控制在 400 行以内、时长不超过 60 分钟，缺陷发现率更高。小 PR 更容易理解和审查，也能减少合并冲突。
- **设定重点**：明确本次审查关注什么，例如功能正确性、软件设计、代码复杂度、测试覆盖、命名规范、注释和文档等。
- **作者自审**：提交 PR 前先自行审查代码，写清 PR 描述和必要的代码注释，说明变更目的和实现思路。
- **自动化前置**：把静态检查（Lint）、类型检查和单元测试等自动化任务交给 CI/CD 流水线，让人工审查专注于设计和逻辑问题；也可以用 [Husky](https://typicode.github.io/husky/) 等 Git hooks 工具在提交前运行轻量检查，把明显问题拦在 PR 之前。
- **建设性反馈**：讨论集中在代码、设计和影响上，以学习和改进为导向。
- **及时响应**：PR 应尽快审查，避免阻塞开发流程。
- **尽早讨论设计**：复杂功能在编码前先讨论整体设计和方案，降低后期大规模重写的风险。

**表格：主流 Git 工作流对比（GitFlow vs. GitHub Flow）**

| 特性/工作流        | [GitFlow](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow) | [GitHub Flow](https://docs.github.com/en/get-started/quickstart/github-flow) |
| :----------------- | :-------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------- |
| **分支模型**       | 多分支（master、develop、feature、release、hotfix）                                     | 极简（main + 短生命周期特性分支）                                            |
| **发布模式**       | 结构化，有专门的 release 分支和 QA 阶段                                                 | 持续集成/部署，合并后即可部署                                                |
| **复杂性**         | 高，分支和合并操作多，需要严格规范                                                      | 低，简单分支和合并，易于理解和实施                                           |
| **团队规模**       | 适合大型团队，需要严格控制和版本化发布                                                  | 适合小型敏捷团队，追求快速迭代和部署                                         |
| **CI/CD 兼容性**   | 较差，多步骤流程可能阻碍持续交付                                                        | 良好，PR 可直接触发自动化测试和部署                                          |
| **合并方式**       | 多条分支之间交叉合并，长期分支容易积累冲突                                              | 短期分支频繁合并到 main，单次冲突范围小                                      |
| **测试方法**       | 主要在 release 分支进行严格测试                                                         | 自动化 CI 测试在特性分支和 PR 上至关重要                                     |
| **热修复**         | 专门的 hotfix 分支，不影响主开发                                                        | 通过特性分支直接从 main 创建和合并                                           |
| **生产稳定性风险** | 较低，因有 release 分支进行阶段性测试                                                   | 较高，若 PR 审查和测试不严格                                                 |
| **工具支持**       | 许多 [Git](https://git-scm.com/) 工具和 GUI 支持                                        | 与 [GitHub](https://github.com/) PR 系统原生集成                             |

GitFlow 提供严格的分支结构和版本化发布，而 GitHub Flow 强调简洁和快速迭代。GitFlow 适用于需要严格版本管理、有明确发布周期（如企业级软件、受监管行业）的大型团队，牺牲了部分灵活性以换取稳定性和可预测性。GitHub Flow 则更适合追求快速迭代、持续交付的敏捷团队，将风险前置到频繁的 PR 审查和自动化测试中。工作流应服务于当前团队和项目，可以根据项目特性和团队现状选择，甚至定制。

代码审查能够发现 bug、提升代码质量、促进知识共享。在 GitHub Flow 这样将所有变更直接合并到 main 的模式下，代码审查是防止缺陷流入主分支的关键质量门禁；PR 中的讨论和反馈，也能把设计决策、最佳实践等隐性知识显性化。高效的代码审查流程配合自动化测试，能够同时提升软件交付的质量和速度。

## **III.7.3 一个可重复的 GitHub Flow 命令序列**

下面的命令把同步、分支、验证和推送串成一个短循环。具体分支名和远程仓库名可以按团队约定调整。

```powershell
git switch main
git pull --ff-only
git switch -c feat/search-cancel

# 修改后
git status --short
git diff --check
pnpm lint
pnpm test
git add src/search tests/search
git commit -m "fix: cancel stale search requests"
git push --set-upstream origin feat/search-cancel
```

PR 描述应记录用户可见结果、验证命令、截图或录屏、风险点和回滚方式。分支上的每次推送都应让 CI 重新验证，合并前由人工阅读 diff 和业务边界。
