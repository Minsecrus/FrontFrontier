# III.7 Git 工作流与团队协作

掌握 [Git](https://git-scm.com/) 命令只是个人操作基础。多人并行开发时，如果缺乏统一的分支与合并约定，很容易出现主干代码无法部署、长周期分支合并冲突失控、线上紧急修复被未完成的新功能阻塞等故障。Git 工作流要解决的核心问题，就是如何管理分支生命周期、何时集成代码、怎样验证并安全发布。

## III.7.1 主流 Git 工作流模式

[GitFlow](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow) 采用严格隔离的多分支模型，将分支划分为两条长期主分支与三类短期支持分支：

- **master**：始终存放随时可部署的生产代码。
- **develop**：汇总日常已完成的新功能，作为下一版本的集成基线。
- **feature**：从 `develop` 切出，用于开发独立功能，完成后合并回 `develop`。
- **release**：从 `develop` 切出，用于版本冻结、集中测试与缺陷修复，就绪后同时合并回 `master` 和 `develop`。
- **hotfix**：从 `master` 切出，用于紧急修复线上故障，验证后同时合并回 `master` 和 `develop`。

这种模式的取舍很鲜明：职责边界清晰，`release` 分支为回归测试与人工 QA 留出了独立缓冲期，`hotfix` 也能绕开开发中的半成品直接修复线上问题，适合有固定发版周期的企业软件或受监管系统。但代价同样明显：分支层级多、交叉合并频繁，长周期存在的 `develop` 与 `release` 分支容易与主线偏离并积累大规模冲突，多步合流也拉长了 CI/CD 的交付链路。

[GitHub Flow](https://docs.github.com/en/get-started/quickstart/github-flow) 大幅简化了分支结构，只保留一条长期可部署的 `main`（或 `master`）主分支，所有开发均围绕短期特性分支展开：

1. 从 `main` 分支切出生命周期很短的特性分支。
2. 在分支上小步提交，每次提交保持逻辑独立且完整。
3. 发起 Pull Request（PR），触发自动化 CI 检查并开展同行代码审查。
4. 审查与测试通过后立即合并回 `main`，随后直接部署或进入待发布状态。

GitHub Flow 消除了多级集成的等待成本，每次变更都在独立 PR 中留痕并触发流水线，非常适合高频交付的 Web 应用团队。但它没有独立的发布冻结分支，所有改动直接合入 `main`：一旦 PR 审查流于形式或自动化测试覆盖不足，破坏性变更就会直接污染主干；同时，多人并行修改相近模块时，仍需频繁同步 `main` 以免积压冲突。

[Trunk-Based Development (TBD)](https://trunkbaseddevelopment.com/)（主干开发）进一步压缩分支生命周期：开发者直接向主干（`main`）做小步提交，或通过存活不超过一两天的极短分支合入，尚未就绪的功能则通过功能开关（Feature Flags）在运行时隐藏。这种做法把合并冲突与分支管理开销降到最低，但高度依赖完备的自动化测试门禁、快速回滚机制与严格的团队工程纪律。

下表对比了 GitFlow 与 GitHub Flow 在分支管理、测试策略与发布节奏上的关键差异：

| 特性/工作流        | [GitFlow](https://www.atlassian.com/git/tutorials/comparing-workflows/gitflow-workflow) | [GitHub Flow](https://docs.github.com/en/get-started/quickstart/github-flow) |
| :----------------- | :-------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------- |
| **分支模型**       | 多分支（master、develop、feature、release、hotfix）                                     | 极简（main + 短生命周期特性分支）                                            |
| **发布模式**       | 结构化，有专门的 release 分支和 QA 阶段                                                 | 持续集成/部署，合并后即可部署                                                |
| **复杂性**         | 高，分支和合并操作多，需要严格规范                                                      | 低，简单分支和合并，易于理解和实施                                           |
| **团队规模**       | 适合大型团队，需要严格控制和版本化发布                                                  | 适合小型敏捷团队，追求快速迭代和部署                                         |
| **CI/CD 兼容性**   | 较差，多步骤流程可能阻碍持续交付                                                        | 良好，PR 可直接触发自动化测试和部署                                          |
| **合并方式**       | 多条分支之间交叉合并，长期分支容易积累冲突                                              | 短期分支频繁合并到 main，单次冲突范围小                                      |
| **测试方法**       | 主要在 release 分支进行严格测试                                                         | 自动化 CI 测试在特性分支和 PR 上至关重要                                     |
| **热修复**         | 专门的 hotfix 分支，不影响主开发                                                        | 通过特性分支直接从 main 创建和合并                                           |
| **生产稳定性风险** | 较低，因有 release 分支进行阶段性测试                                                   | 较高，若 PR 审查和测试不严格                                                 |
| **工具支持**       | 许多 [Git](https://git-scm.com/) 工具和 GUI 支持                                        | 与 [GitHub](https://github.com/) PR 系统原生集成                             |

选型时不必照搬教条：按版本批次交付、依赖人工验收的团队可采用 GitFlow 或带发布分支的变体；追求每日多次部署、具备可靠 CI 的 Web 团队则更适合 GitHub Flow 或主干开发。

## III.7.2 代码审查（Code Review）的重要性和流程

在 GitHub Flow 或主干开发这类将改动直接合入 `main` 的工作流中，代码审查是拦截逻辑漏洞、性能退化与安全隐患的最后一道人工防线；同时，PR 中的讨论也能同步模块上下文、对齐架构边界，避免核心逻辑只有单人知晓。

为了让代码审查真正发挥拦截与对齐作用，而非沦为形式化的“点 Approve”，建议落实以下执行准则：

- **明确流程**：约定 PR 的状态流转（草稿 Draft、待审查、请求修改、批准、合并）及各阶段的准入条件。
- **控制规模**：单次审查控制在 400 行变更以内、时长不超过 60 分钟。小粒度 PR 更容易看清边界条件，缺陷检出率明显高于动辄上千行的大合并，也便于出错后精准回滚。
- **设定重点**：人工审查应聚焦于静态工具无法判断的问题——业务语义是否正确、状态与异常边界是否闭合、模块职责是否清晰、测试是否覆盖了关键路径。
- **作者自审**：发起审查前，作者应先通读一遍 Diff，并在 PR 描述中写明变更背景、技术方案、影响范围与验证结果。
- **自动化前置**：把代码格式、Lint、类型检查和单元测试交给 CI 流水线与 [Husky](https://typicode.github.io/husky/) 等本地 Git hooks 自动拦截，不要让审查者充当“人肉 Linter”。
- **建设性反馈**：评论针对具体代码行、设计取舍和潜在影响展开，区分“必须修改的阻塞项（Blocker）”与“可选的改进建议（Nit）”。
- **及时响应**：优先处理待审 PR，避免长周期搁置导致分支偏离主干、产生二次合并冲突。
- **尽早讨论设计**：涉及跨模块改造或公共 API 变更时，先通过技术方案文档（RFC）或轻量讨论对齐方向，避免写完上千行代码后才在 PR 阶段推翻重写。

## III.7.3 一个可重复的 GitHub Flow 命令序列

下面的命令把同步、分支、验证和推送串成一个短循环。具体分支名和远程仓库名可以按团队约定调整。

```powershell
git switch main
git pull --ff-only
git switch -c feat/search-cancel

# 修改后
git status --short
git diff --check
pnpm lint
pnpm test
git add src/search tests/search
git commit -m "fix: cancel stale search requests"
git push --set-upstream origin feat/search-cancel
```

PR 描述应记录用户可见结果、验证命令、截图或录屏、风险点和回滚方式。分支上的每次推送都应让 CI 重新验证，合并前由人工阅读 diff 和业务边界。
